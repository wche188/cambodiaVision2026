## Bugs Found and Fixed (this QA pass)

### BUG 1 — `/api/patients` POST: invalid `gender` not validated
**Symptom:** API accepts any value for `gender`, MySQL silently truncates non-enum values, app returns generic 400 "Invalid input" with no useful message.

**Root cause:** `app/api/patients/route.js` only validated `age`, not `gender`. The DB enum is `('Male','Female','Child')` but anything else gets a `WARN_DATA_TRUNCATED` from MySQL.

**Fix:** Added enum validation in the route handler — rejects with 400 and a clear message listing the allowed values.

### BUG 2 — `/api/patients/report` accessible to station managers
**Symptom:** Doctor (station_manager role) could call `GET /api/patients/report` and get the full admin analytics report. This endpoint contains aggregate counts across all patients, all stations, and daily registration trends — should be admin-only.

**Root cause:** `middleware.js` `ADMIN_PATHS` array was `['/admin', '/api/admin']` — missing `/api/patients/report`.

**Fix:** Added `/api/patients/report` to `ADMIN_PATHS`. Doctor now correctly gets 403.

### BUG 3 — `/api/patients` POST: missing `registration_date` returns 400
**Symptom:** Volunteer creating a patient without explicitly setting `registration_date` got 400 "Invalid input" with no detail. Schema has `registration_date NOT NULL` but the API only `|| null`-ed the value, never defaulted it.

**Root cause:** `app/api/patients/route.js` line 129 had `registration_date || null` instead of defaulting to today.

**Fix:** Changed to `registration_date || new Date().toISOString().split('T')[0]`. Now the API auto-sets today if missing, matching the volunteer UX (they shouldn't have to set the date).

### BUG 4 — `.docx` templates UTF-8 corrupted
**Symptom:** `GET /api/generate-pdf/<id>?type=registration` returns 500 with `End of data reached (data length = 549835, asked index = 598406). Corrupted zip`.

**Root cause:** Both template files in the repo (`registration_template.docx`, `surgery_template.docx`) had UTF-8 replacement characters (`U+FFFD`) scattered throughout — same root cause as the previously-fixed `app/icon.png` and `public/logo.jpeg` corruption. Templates were 21% corrupted. PizZip couldn't parse the resulting "zip" structure.

**Fix:** Restored both templates from `.git.backup-pre-claude-cleanup/HEAD` (clean originals, 0% corruption). Also removed the stray `registration_template_backup_1782731346881.docx` file that shouldn't have been in the repo.

### BUG 5 — Surgery form download broken for station managers
**Symptom:** Surgery station manager (e.g. "doctor" account) clicks the "Surgery Form" button on a patient page. Instead of downloading the .docx, they get redirected to `/station`. Form does not download. Admin downloads work fine.

**Root cause:** `middleware.js` `STATION_MANAGER_PATHS` did not include `/api/generate-pdf`. So when the station manager hit `/api/generate-pdf/28?type=surgery`, middleware treated it as an unallowed path and redirected to `/station`. The route handler itself was correctly written to allow station managers (line 32 checks `session.role !== 'admin' && session.role !== 'station_manager'`), so the bug was purely in the middleware allowlist.

**Why QA missed it:** The original QA test only hit `/api/generate-pdf` as admin. The station manager branch was not exercised.

**Fix:** Added `/api/generate-pdf` to `STATION_MANAGER_PATHS` in `middleware.js`. Verified: admin, station manager, and volunteer all get correct responses (admin/station manager → 200, volunteer → 403 for surgery only).

### BUG 6 — `Prepare_for_Surgery` and `Surgery_Completed` statuses never set
**Symptom:** The dashboard filter dropdown shows `Prepare_for_Surgery` and `Surgery_Completed` as filter options, but the count is always 0 and the filtered list is always empty — even for patients who've had surgery form downloaded and surgery record submitted. The state machine in `lib/status-pipeline.js` defined the allowed transitions, but no code ever performed the UPDATE.

**Root cause:** Two missing status writes:
- `app/api/generate-pdf/[patientId]/route.js` only updated status to `Form_Printed` when `type=registration` was downloaded. No equivalent for `type=surgery` setting `Prepare_for_Surgery`.
- `app/api/patients/[id]/surgery-record/route.js` updated `stations_visited` to include `Surgery` but never touched `status`. No code set `Surgery_Completed`.

**Fix:**
- In `app/api/generate-pdf/[patientId]/route.js`: when `type === 'surgery'`, use the existing `isValidTransition` helper to check the state machine, then UPDATE status to `Prepare_for_Surgery`. Allowed sources: `Surgery_Eligible`, `Surgery_Scheduled`.
- In `app/api/patients/[id]/surgery-record/route.js`: fetch `status` alongside `stations_visited`, and after inserting the record, UPDATE status to `Surgery_Completed` if the transition is allowed. Allowed sources: `Prepare_for_Surgery`, `Surgery_Scheduled`.

**Verification (end-to-end):**
- Started: `Surgery_Eligible` → download surgery form → `Prepare_for_Surgery` → submit surgery record → `Surgery_Completed` ✓
- Negative case: `Registered` patient downloads surgery form → status stays `Registered` (state machine blocks the invalid transition) ✓
- Re-download on already-`Surgery_Completed` patient → status unchanged (no further transition) ✓
